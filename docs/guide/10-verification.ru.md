# Проверка: трейсы и логи

[Документация](../README.ru.md) / [Руководство](./README.ru.md) / 10 · [English](./10-verification.md)

## Три уровня доказательств

| Проверка | Что подтверждает |
| :--- | :--- |
| Лог и резервная копия | Какие шаги запрошены, что записано и какие ошибки сохранены. |
| Readback | Текущее значение доступного реестра, ресурса, WMI или аппаратного регистра. |
| Трасса и измерения | Где и сколько выполнялась обработка; как изменилась конкретная нагрузка. |

Эти уровни дополняют друг друга. Совпадение регистра IMOD с введённым числом не является измерением задержки мыши. Сохранённая affinity не подтверждает размещение каждого DPC.

## ISR/DPC через ETW

Установите Windows Performance Toolkit. В повышенной консоли можно записать короткую трассу:

```powershell
xperf -on PROC_THREAD+LOADER+INTERRUPT+DPC
# Воспроизведите короткий, заранее выбранный сценарий.
xperf -d trace.etl
xperf -i trace.etl -a dpcisr > report.txt
```

Действие `dpcisr` строит сводку ISR/DPC: [описание Microsoft](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/the-dpc-isr-action). Для анализа отдельных событий и CPU откройте ETL в Windows Performance Analyzer. Текстовую сводку не считайте автоматически доказательством полного распределения по ядрам.

Сравните активные модули, длительности, CPU и работу потоков приложения. Не объявляйте фиксированные имена потоков, длительности обработчиков или число IRQ эталоном для всех версий Windows и драйверов.

## Честное сравнение

1. Запишите версии Windows, драйвера, настройки и исходную резервную копию.
2. Выберите воспроизводимую нагрузку и измеряемый показатель: распределение времени кадра, загрузку CPU, потери пакетов или задержку устройства.
3. Измените один фактор, выполните необходимую перезагрузку и повторите несколько сопоставимых прогонов.
4. Сохраните трассы и результаты, включая ухудшения и нестабильность.

Повторные прогоны помогают отличить устойчивое изменение от обычного разброса. При неожиданном распределении по CPU сверьте экземпляр устройства, применённую политику и поведение драйвера с трассой.

## Локальный QA проекта

Разработческий стенд проверяет модели устройств, защитные пути и интерфейс в режиме read-only. Скриншоты подтверждают только показанное состояние; их нужно просматривать. Сравнение MATCH означает совпадение пикселей.

Виртуальные прогоны не проверяют загрузку настоящего драйвера, MMIO/readback на железе, запись настроек Windows, перезагрузку или пробуждение устройства. Масштабы 100/125/150% на стенде моделируют раскладку, а не реальные переходы DPI Windows. Размер тестового окна ограничивается доступным экраном и явно записывается в отчёт.

Подробности: [сборка и разработка](../DEVELOPMENT.ru.md). Реальное железо проверяется отдельно с понятным исходным состоянием и способом восстановления.
