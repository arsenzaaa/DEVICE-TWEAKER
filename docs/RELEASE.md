# Релиз DEVICE TWEAKER

Порядок сборки, проверки файлов и публикации релиза.

## Структура репозитория

```text
DEVICE-TWEAKER/
  README.md, README.en.md    описание программы
  CHANGELOG.md, .en.md       история изменений
  docs/                      настройки, разработка, выпуск, тексты релизов
  src/                       исходники, драйвер, скрипты сборки
  dev/qa/                    тесты, тест-панель и QA
```

Команды сборки ниже выполняются из папки `src/`.

## Локальная сборка пакета

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Flavor both -Configuration Release -SkipImodDriverBuild
```

Готовый набор будет здесь:

`bin\ReleasePackages\v<InformationalVersion>\`

На GitHub Release прикрепляются:

- `DEVICE.TWEAKER.exe`
- `DEVICE.TWEAKER.SelfContained.exe`
- `SHA256SUMS.txt`
- `DEVICE.TWEAKER.Source.v<Version>.zip`
- `SOURCE-SHA256SUMS.txt`

Архив исходников для 0.0.4 сохраняется рядом с EXE под именем `DEVICE.TWEAKER.Source.v0.0.4.zip`. Его SHA-256 записывается в `SOURCE-SHA256SUMS.txt`. Это отдельный снимок публичных исходников; личные материалы, результаты QA и каталоги сборки в него не входят. Перед публикацией нужно сверить его состав и SHA-256 с текущими файлами проекта.

Драйвер `DTIMOD.sys` и загрузчик KDU уже встроены в EXE. Отдельные копии в assets не нужны.

## Публикация

### Замена текущей 0.0.4

1. Выполнить локальный QA и сверить тексты, исходники и оба EXE. Версия в проекте и манифесте остаётся 0.0.4.
2. Проверить набор через `dev/qa/Test-ReleasePackage.ps1`. Сохранить SHA-256, отчёт QA и список исходников, из которых выполнена сборка.
3. После проверки автором отправить окончательный коммит в `main`. Старые релиз и тег `v0.0.4` сохранить локально, затем удалить с GitHub.
4. Создать тег `v0.0.4` на окончательном коммите. Создать новый черновик релиза, добавить описание, оба EXE, оба файла SHA-256 и архив исходников.
5. Скачать файлы черновика, сверить контрольные суммы и исходный коммит. Опубликовать релиз и отметить его последним выпуском.

Выпуски 0.0.1-0.0.3 остаются на месте. Публичные резервные теги и ветки не создаются. Историю `main` переписывать не требуется.

Workflow `Release package` запускается только вручную и создаёт новый черновик; существующий релиз он не заменяет. Создание тега само по себе не запускает упаковку. Для подготовленного локально набора повторная сборка в workflow не нужна. Локальные скрипты ничего не публикуют.

### Новый номер версии

1. Сверить изменения с исходным кодом и обновить версию в `src/DeviceTweakerCS.csproj`, `src/assets/app.manifest`, README, `CHANGELOG.md` / `CHANGELOG.en.md` и `docs/releases/v*.md`.
2. Проверить сборку, тесты и интерфейс, затем отправить окончательный коммит в `main` и дождаться успешного CI.
3. Создать и отправить новый тег `v<Version>` на этот коммит. Не использовать прежний тег для новой сборки.
4. Вручную запустить workflow `Release package`, указав новый тег. Он проверит соответствие тега версии проекта, выполнит тесты, соберёт два EXE, проверит SHA-256 и создаст **черновик** релиза. В его описании будет указан исходный коммит.
5. Скачать файлы черновика, сверить контрольные суммы, проверить запуск обеих сборок и опубликовать черновик. Если после создания тега нужно изменить код, подготовить новую версию и новый тег.

## Проверка после публикации

1. Сверить опубликованные SHA-256 обоих EXE с `SHA256SUMS.txt` из того же релиза.
2. Проверить ссылки README, текст релиза и состав assets на GitHub.
3. Запустить автономную версию от имени администратора и проверить основные сценарии.
