# Покрытие QA

[Команды](../README.ru.md) · [Workbench](../WORKBENCH.ru.md) · [English](README.md)

Общий прогон вызывает эти проверки последовательно. Выбирайте отдельную проверку по затронутому поведению. Для нативных моделей нужны C++ Build Tools и Windows SDK.

## Что проверяется

- **Сборка**: Обычная и разработческая версии; предупреждения считаются ошибками.
- **xUnit**: Маски, парсинг, локализация, профили и блокировка настоящих методов записи.
- **WMI / RSS**: Общая последовательность запроса, записи и повторного чтения WMI на подставном backend; неподдерживаемая возможность, отказы и несовпадение readback. Настоящий PowerShell-код RSS с подменёнными функциями Get-NetAdapter / Get-NetAdapterRss. Пропуск Wi-Fi, неполное чтение и реальные расхождения проверяются отдельно.
- **ID приложения**: В логах и crash report сохраняются MVID сборки и SHA-256 запущенного EXE. Проверка пакета сверяет SHA-256 с файлом.
- **IRQ Mode**: Разбор PCI MSI / MSI-X Enable и выделенных CM_RESOURCE_LIST, один IRQ для обоих режимов, повреждённые данные, ошибки чтения, несовпадение устройства. QA не открывает DTIMOD; живое чтение PCI проверяется вручную.
- **Реальные образцы ресурсов**: Шесть сохранённых ответов Windows 10: USB / GPU / NIC / NVMe / SATA. Разбор обоих списков raw + translated, сверка типов и отказ при повреждённом хвосте. Во время QA используется JSON, обращения к драйверу нет.
- **Подготовка DTIMOD**: Параллельные ветки одного процесса проходят общий lock. Проверка на отдельном тестовом файле с настоящими эксклюзивными файловыми дескрипторами.
- **DTIMOD**: Сверка исходников и `.sys` с `IMOD/DTIMOD.build.json`. Изменённый исходник или бинарник останавливает QA; отдельные испорченные копии проверяют этот отказ. После изменений драйвера: `publish-variants.ps1 -BuildDriverOnly`.
- **Жизненный цикл DTIMOD**: Общая политика GUI / скрипта: чтение без загрузки, таймаут без SCM fallback, протокол и ID сборки, конкурирующие операции и abandoned mutex. Только подставные backends и отдельные тестовые mutex.
- **Нативная модель**: Настоящие функции DriverEntry / dispatch / MMIO собираются с fake kernel API: регистрация обработчика выгрузки, ответ протокола, размеры, выравнивание, отказ mapping и освобождение отображения. Запись принимается только внутри памяти, которую Windows выделила устройству: границы, порты, переполнение адреса, повреждённый список ресурсов. Три намеренные поломки (удаление регистрации обработчика выгрузки, запись через конец диапазона и обход проверки диапазона при записи) обнаруживаются утверждениями модели.
- **KDU**: пара EXE/DLL, версии, хеши и входные файлы из [манифеста upstream](../../../src/IMOD/KDU/upstream.json). Подмена исходника, EXE или базы проверяется в отдельных копиях.
- **Применение**: Общий DeviceSettingsWriter: MSI, лимит, приоритет, двоичная маска, Windows Default на реестре в памяти.
- **Идентичность драйвера**: Имена программы/автозапуска, закреплённый SYS, отказ при загруженном legacy-устройстве и неизменяемый запрет QA; миграции служб нет.
- **Автозапуск**: `profile.json` ↔ настройки программы, перенос старого скрипта из AppData и сохранённых бэкапов без потери значений, XML задачи Планировщика (SYSTEM, вход, выход из сна, подключение USB/HID). Настоящий `ApplyIMOD.ps1` запускается в PowerShell 5.1 до чтения профиля и компилирует общий runtime; задача не регистрируется, драйвер не загружается.
- **Восстановление**: Общий BackupRestoreService: JSON версии 1, предварительный снимок, запись, readback и откат.
- **План питания**: Общий компонент восстановления: AC/DC отдельно, сохранённый GUID, активный/неактивный план и отказы API на модели.
- **IMOD / NIC ITR**: Один код записи регистров для программы и автозапуска: адреса, маски, порядок, ошибки чтения/записи/сравнения на модели. Раскладка xHCI и карта interrupter'ов на поддельной памяти контроллера: TRB эндпоинта важнее Slot Context, хабы пропускаются, RTSOFF за пределами BAR отклоняется.
- **CPU**: Общий планировщик на синтетических топологиях: SMT, P/E, CCD/CCX, изоляция GPU и input.
- **Polling**: Синтетические интервалы, подтверждение и смена частоты; низкая активность клавиатуры не подменяет endpoint rate.
- **Отчёты**: Одновременное чтение/обновление JSON и отсутствие тест-панели в обычной сборке.
- **Чувствительность**: Семнадцать испорченных копий: адрес I225, NIC readback, счётчик IMOD, readback бэкапа, выбор пары GPU, раннее снижение polling, неверный AC/DC, активация неактивного плана, снятие read-only через окружение, подмена MSI-X Enable размером таблицы, пропуск отличия в один пиксель, освобождение шрифта до контролов, отказ второго списка ресурсов Windows, загрузка до проверки существующего устройства, SCM после таймаута KDU, потеря значений NIC ITR в профиле автозапуска и выбор interrupter'а по Slot Context вместо TRB. Нужные тесты должны упасть; ошибка сборки не засчитывается.
- **GUI**: RU/EN, геометрия, диалоги, навигация, тест-панель и виртуальные сценарии.
- **Стенд разработки**: Два сценария по два запуска: native-снимки, переход, изменение и восстановление тестового JSON, реальное исключение подставного хранилища, точное сравнение контрольных снимков. Просмотр дизайна фиксируется отдельно.
- **Контролы обычной сборки**: Маршрутизация клавиш выпадающего списка, выбор и закрытие popup, Ctrl+Z/Home/End в редакторе, RU→EN→RU с сохранением исходных строк. Восемь снимков normal/hover/focus/disabled; физический ввод не используется.
- **Инвентарь исходников**: Активные C#-файлы обычной сборки, методы и строки интерфейса через Roslyn; список помогает ручной сверке, сам по себе не означает проверки всей логики.
- **Скрытый запуск**: Независимый отказ в скрипте и EXE при неверном desktop, точная передача кода ошибки и завершение потомков после таймаута.
- **Компоновка**: Шесть сценариев RU/EN × 100/125/150%, настоящие WinForms-контролы, отрисованные подписи кнопок и диалог RESTORE. Масштабируется компоновка в QA-сборке; настройки DPI Windows не меняются, переходы между мониторами не проверяются.
- **Логи**: Формат и завершение сессии, отклонение неожиданных ERROR/FATAL. Подставленные ошибки принимаются только в успешно проверенном сценарии; образцы диалогов помечены отдельно.
- **Ресурсы**: 20 обновлений списка в обычном EXE с read-only, подтверждение каждого нажатия и REFRESH.DONE, ожидание стабилизации handles/GDI/USER, замеры памяти.
- **Доказательства**: Повторная сверка TRX, обязательных этапов и классов тестов, семнадцати регрессий C#, трёх нативных регрессий, шести сценариев масштаба, завершённых циклов и хешей файлов.

Проверки восстановления по умолчанию используют синтетический JSON. Для дополнительной проверки собственных бэкапов на хранилище в памяти явно передайте `-BackupSamples <каталог>` в `Invoke-Qa.ps1`. Оригиналы не меняются. Реальные бэкапы не требуются, не поставляются со стендом и автоматически не выбираются; их пути могут попасть в локальные TRX-отчёты.

Виртуальные APPLY/BACKUP/RESTORE тест-панели отдельно помечены как проверки модели. Настоящее применение на железе, readback драйвера и живое измерение Raw Input остаются `SKIPPED`.

## Нативная диагностика жизненного цикла контроллера

`Test-NativeDriverModel.ps1 -ProbeRemovalRace` добавляет два управляемых чередования после запроса ресурсов: удаление устройства и передачу старого диапазона другому модельному владельцу. Настоящие C-функции драйвера выполняются с подставными API ядра; во втором случае отображается отдельный буфер памяти нового владельца. SYS не загружается, обращений к оборудованию нет.

`removal-probe.json` получает статус `EXPOSURE_OBSERVED`, если модель обнаружила запись после инвалидизации, иначе `NOT_OBSERVED`. Ни один из этих результатов не подтверждает PnP-синхронизацию Windows. Диагностика отделена от обычного `PASS` нативных регрессий и по умолчанию не запускается. Предпосылки модели нужно сохранять и сверять с контрактом времени жизни устройств и ресурсов Windows.

`Test-NativeDriverModel.ps1 -OutputDirectory .\local\native-lifecycle -ProbeDeviceLifecycle` выполняет 27 сценариев с настоящими функциями dispatch, доступа к регистрам и записи в устройство. Потеря действительности ресурсов задаётся после query, перед mapping, после mapping или после обращения. Проверяются чтения и записи, предпосылки удаления/остановки/переназначения, отказы, отмена, новые диапазоны и очистка. Подставные API не реализуют порядок уведомлений Windows, управление питанием и путь открытия/опроса PCI. Отказ запроса ресурсов - проверяемый вход, а не гарантия отказа любого такого запроса Windows на остановленном устройстве.

В `lifecycle-probe.json` сохраняются каждый сценарий и хеши исходников и входов диагностики. `UNCOORDINATED_ACCESS_OBSERVED` означает попытку обращения к регистру после заданной инвалидизации; успешный mapping в заглушке не предсказывает результат на исчезнувшем оборудовании. Успешные assertions подтверждают ожидания диагностики, а не исправление PnP-защиты. Отрицательные контроли задают изменение после обращения: предшествующий доступ не должен считаться устаревшим. Диагностика запускается отдельно от `-ProbeRemovalRace` и `-InjectRegression`.

## Результаты

В `src/tmp/qa/run_*/` сохраняются `qa.json`, `inputs.json`, копия входных файлов, TRX, логи, отчёты намеренных поломок, скриншоты GUI, `layout/layout.json`, `resources/resources.json`, `desktop-contracts/contracts.json`, `isolation/desktop.json` и `evidence.json`. В `desktop.json` записываются имя desktop, проверки активного desktop и подтверждение уборки потомков.

Отсутствующий результат, пропущенные обязательные тесты, изменённый снимок исходников, ненулевой код worker или неподтверждённый цикл не считаются успешной проверкой. `evidence.json` проверяет полноту и соответствие артефактов. Достоверность результата зависит от целостности самих проверок и отчётов. Скриншоты требуется просмотреть отдельно: автоматическая проверка изображения и геометрии не оценивает весь дизайн.

В матрице компоновки `main.png` / `restore.png` снимаются через native PrintWindow в пределах геометрии дисплея; если окно выше этой области, снимок явно отмечен `fullWindow=false` и содержит только viewport. Невидимый desktop при этом не выводится на дисплей. Отдельный `*.layout.png` содержит полную диагностическую отрисовку DrawToBitmap: она помогает проверять компоновку, но может отличаться в native-тексте и рамке DWM и не выдаётся за полный визуальный снимок. Большие белые области считаются ошибкой native capture.

`PASS` относится к перечисленным проверкам. Количество тестов не означает проверку любого оборудования. `-SkipGui` даёт `PARTIAL`; сбой обязательного этапа даёт `FAIL` и ненулевой код завершения. Скрипт закрывает только собственные процессы и не выполняет коммиты, push или публикацию.

Готовый локальный набор EXE проверяется отдельно:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\dev\qa\Test-ReleasePackage.ps1 -PackageDirectory ".\src\bin\ReleasePackages\v0.1.0"
```

Проверяются SHA-256, версия, запуск обоих EXE в probe, встроенный драйвер и отсутствие тест-панели. Главное окно и применение настроек не запускаются.

Нативная модель компилирует production-обработчик и функцию записи вместе с dispatch и разбором диапазонов. Проверяются допустимая запись, выход за диапазон, отмена, неверные ширина/версия/IRQL, ошибки PCI и ресурсов, повреждённые списки, ошибка отображения памяти и освобождение ссылок/рабочего элемента. Поиск PCI, получение ресурсов, очередь и отображение памяти подменены; планирование ядра и физические устройства этой моделью не проверяются.

`Test-BuildUserData.ps1` проверяет сохранность данных при чистой сборке на временных папках EXE с подставным publisher. Проверяются ошибка перемещения второй папки, ошибка на следующем варианте EXE, отказ publisher и успешная сборка. Приложение не запускается, драйвер не подписывается, реальные бэкапы и логи не используются; CI запускает проверку отдельно.

В полный набор стенда входят `refresh-reuse`, `refresh-reuse-lifecycle` и `refresh-reuse-lifecycle-amd`. Они проверяют сохранение экземпляров карточек, свежие настройки и исходные значения редакторов, черновики/фокус/прокрутку, адресацию виртуального APPLY, отключение/переподключение, смену ролей, отказ обнаружения, изменение топологии во время чтения и очистку устаревшего RSS-выбора. Это синтетические read-only сценарии, а не проверка физического hotplug.

QA-launcher допускает один независимый прогон в сессии Windows. Подготовка блокируется до создания снимка/сборки. Invoke-DevSession создаёт ограниченный private job до проверки кэша и компиляции; сценарий и дочерние процессы компилятора работают в том же job. Вложенные проверки остаются внутри существующего private job. Worker и его потомки имеют пониженный приоритет и лимит commit всего job не выше 3 ГиБ (также ограниченный объёмом ОЗУ). Устойчивая нехватка физической памяти или commit приводит к остановке только собственного job. В `isolation/resources.json` сохраняются лимит, пиковый commit job и минимальный наблюдаемый запас памяти. Это защита хоста, а не замер производительности или гарантия от любых причин нагрузки. Прямые ручные команды сборки выполняются вне этого launcher.

`Test-QaWorkload.ps1 -OutputDirectory local/qa-workload` проверяет блокировку параллельных запусков, границы памяти, остановку при имитации её нехватки и завершение собственных дочерних процессов. Используются небольшие процессы, ОЗУ не заполняется. Эту короткую проверку запускают с обычного desktop; видимые окна она не создаёт.

`Test-QaDevPreparation.ps1 -OutputDirectory local/qa-preparation` проверяет настоящую точку входа стенда с небольшой подстановкой на границе сборки. Подтверждает, что подготовка и её дочерний процесс наследуют ограниченный private job, а ошибка подготовки доходит до вызывающего процесса. Компилятор и GUI программы не запускаются. Для каждого прогона нужен новый каталог результата.

Для небольших прогонов матрицы у шага `audit-hardware-matrix` задайте `device` со списком ID через запятую, например `system-13,system-14,cpu-00`. ID соответствуют индексам каталога, записанным в отчётах матрицы. Неизвестные, повторяющиеся и пустые ID останавливают проверку; без фильтра выполняется вся матрица. Группы запускайте последовательно в отдельных процессах.
